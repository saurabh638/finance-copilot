# DECISIONS ARCHIVE

Every decision that no longer constrains new work, kept exactly as it was written and in the order it was
made: how one milestone's implementation was shaped, bugs the walkthroughs found, choices a later milestone
superseded, and the platform and process decisions that ARCHITECTURE.md, README.md, CODING_STANDARDS.md and
RULES.md now carry.

Nothing has been deleted: every entry that has ever appeared in DECISIONS.md is either in the short list
there or here. Read this when changing something these entries touch, or when wondering why something is the
way it is. It is not part of the read-every-session set.

| Date | Decision | Why |
| --- | --- | --- |
| 2026-10-04 | Python and FastAPI backend, React and TypeScript frontend | PDF and statement parsing is far stronger in Python; frontend ports to React Native later |
| 2026-10-04 | Sync SQLAlchemy 2.0 with psycopg 3, not async | Simpler and less error-prone for a single-user app built with a coding model |
| 2026-10-04 | Everything runs in Docker; host needs only Git and Docker | Zero local toolchain setup, and local mirrors production |
| 2026-10-04 | No Redis, Celery, microservices or Kubernetes | Added only when something actually hurts |
| 2026-10-04 | Real balances and statements stay out of git (seed_local.json, data/samples, backups ignored) | Privacy; the repository may become shared |
| 2026-10-04 | Deploy to a budget VPS behind Caddy, backups kept off the server | Free tiers sleep or expire; the data is financial history and needs a stable home |
| 2026-10-04 | Work proceeds one milestone at a time with plan approval and a completion approval | Prevents large unreviewed changes from a coding model |
| 2026-10-04 | A dedicated `finance_test` database is created by the Postgres init script; tests run against real Postgres | Integration tests need a real database, and development data must stay untouched |
| 2026-10-04 | The backend container entrypoint runs `alembic upgrade head` before starting | A fresh database is always migrated, with no manual step |
| 2026-10-04 | The frontend health check reads only the HTTP status, not the JSON body | Avoids hand-writing a duplicate of the server schema; generated OpenAPI types come later |
| 2026-10-04 | The frontend mirrors only the money formatter, not a parser | The UI formats what the API sends; it never parses or does money arithmetic |
| 2026-10-04 | The M1 health placeholder (`HealthStatus`) was removed in M3b | The real login and home screens replace the placeholder page, so it became dead code |
| 2026-10-04 | Testing Library cleanup is registered explicitly in the test setup | Vitest runs without globals, so the library cannot auto-register it and the DOM leaked between tests |
| 2026-10-04 | `loan` is in `AccountType` even though MILESTONES.md M4 lists only eight kinds | ARCHITECTURE.md treats loans as accounts; the CHECK makes it cheap to allow now and impossible to forget later |
| 2026-10-04 | M4 was split into M4a (accounts) and M4b (interest rates) after the plan review | The account model and CRUD already exceed one reviewable step, and rate history needs its own tests |
| 2026-10-04 | The rate schema quantises to the column's scale | The session is `expire_on_commit=False`, so a create echoed 7.1 while a later read returned 7.1000; the same record must not read differently per endpoint |
| 2026-10-04 | Frontend API types are generated from the live OpenAPI schema and the generator is called pinned through `npx`, not added as a devDependency; the generated file is committed and excluded from ESLint, but still Prettier-formatted and typechecked | `openapi-typescript` 7 peers `typescript` ^5 and this project is on 6. Installing it with `--legacy-peer-deps` churned 90 lines of unrelated lock entries and broke `npm ci` in the image build. Committing the output means nothing depends on the generator at run time or when the backend is down |
| 2026-10-04 | The accounts screen replaces the placeholder home page | Same reasoning as M3b removing the M1 health placeholder: a screen that no longer matches the product is dead weight |
| 2026-10-04 | An account's first interest rate is recorded from its opening date, in a second call after the account is created | The account is the object that matters, so a rate failure leaves it intact and reports exactly what did not save, rather than losing both to one transaction. The user is never asked for the same date twice |
| 2026-10-04 | Form option lists are declared `satisfies Record<Enum, string>` | A member added on the server becomes a compile error in the form, instead of an account type the UI silently cannot create |
| 2026-10-04 | The add and edit forms share one `AccountFields` component | Ten duplicated fields would drift apart, and the add form's tests are the safety net for the shared part |
| 2026-10-04 | An empty optional day is sent as `null`, never as `0` | `Number('')` is 0, which the server rejects: a credit card could not be saved unless both card days were filled. Empty means "not set", and zero is not a day of any month |
| 2026-10-04 | The seed skips an account that already exists by name instead of updating it | An opening balance that has since been corrected must never be overwritten by re-running a setup command; the fix belongs in the UI, where the change is visible |
| 2026-10-04 | Placeholder accounts carry a ` (demo)` suffix and a purpose note, and `--remove-demo` matches only that | Dummy data has to be removable later with no chance of deleting a real account that happens to share a name |
| 2026-10-04 | The seed writes nothing until all six accounts have been answered | An interrupted run, including piped input that ends early, must leave no half-created set behind |
| 2026-10-04 | The placeholder balance and date are fixed constants, not "today" | The placeholder run must give the same result on every machine and every day, so it can be tested and reasoned about |
| 2026-10-04 | A typed balance in the seed goes through `core/money.parse_paise`, and the prompt re-asks until it is accepted | The command-line tool must not grow a second money reader, and a typo must not become a wrong paise value |
| 2026-10-04 | Backups are `pg_dump --format=custom` in a dated file under `backups/`, and the script reads every file back before trusting it | A dump that cannot be listed is not a backup, and discovering that at restore time is discovering it too late |
| 2026-10-04 | `restore.sh` refuses the live database; restoring into a scratch copy is the only path it offers, and replacing live data is a documented manual sequence | One typo must not be able to replace financial history. Promotion should be a decision somebody makes, not a command away |
| 2026-10-04 | The backup scripts run through the `postgres:16` db container, so the client matches the server | `pg_dump` refuses to dump a newer server, and the backend image has no client at all; a mismatched client is a trap that only springs on the day it is needed |
| 2026-10-04 | The round-trip row-count check is a script rather than a pytest test | The host has only Git and Docker, so the check runs where the correct client already is. It is documented with the daily commands instead of hiding in a gate it cannot join |
| 2026-10-04 | The database name `finance_restore` is reserved for the scratch restore, and `finance_promote` for the documented promotion | The scripts drop and recreate those names on demand, so nothing else may own them |
| 2026-10-04 | `category_id`, `import_batch_id` and `fingerprint` are left out of the models until M10 and M15 | Empty columns nothing writes are worse than a one-line migration later |
| 2026-10-05 | The signed-in app is a two-item tab bar with the current screen in `useState`; no router is introduced | Two screens with no deep-link need do not justify a dependency (RULES.md section 3.7). ARCHITECTURE.md lists React Router in the stack, so this is a deliberate postponement rather than an omission: it should arrive with M11's check-in screen, when a URL starts to mean something |
| 2026-10-05 | The app opens on Transactions, and the recording form starts closed | Recording is the daily action, so the list of what was just recorded is the screen to land on; the form is one tap away and stays open for the next entry |
| 2026-10-05 | The shared field components (`Field`, `TextField`, `SelectField`) moved from `features/accounts` to `components/`, and the accounts header became a shared `PageHeader` | CODING_STANDARDS.md section 4.1 puts reusable UI in `components/`; the alternative was a second feature importing out of the first, and two screens each growing their own title, signed-in line and Log out button |
| 2026-10-05 | The list is paged with `useInfiniteQuery` and a Load more button; a page shorter than the page size ends the list | The server already offers limit and offset, the offset is derived from the page count rather than kept by hand, and one button works on a phone where page numbers do not |
| 2026-10-05 | A saved form is cleared by remounting it (the page bumps a key), not by the form resetting its own fields | One mechanism, owned by the screen that knows the save succeeded, and no risk of clearing a form on a save that failed |
| 2026-10-05 | The screen sends only the filters that are set | An empty date sent as blank text would be an invalid value for the server to reject; leaving it out means the same thing as not filtering |
| 2026-10-05 | Save stays disabled while nothing has changed, and money that cannot be parsed yet counts as a change in progress | Half-typed money during render threw and blanked the editor. A field mid-edit is not a reason to go dead: submit it and let validation explain, which is what the tests now pin |
| 2026-10-05 | `TransactionList.tsx` was removed and the page maps rows directly | The row owns its editor now, exactly as `AccountRow` owns `AccountEditor`; keeping the list in between only forwarded props |
| 2026-10-05 | `Unaccounted for spending` and `Unrecorded income` live in the write-off's note, with `category_id` NULL until M10 | The sign of the difference already says which of the two it is, so the wording costs nothing now and M10 replaces it with the real categories rather than dragging them forward |
| 2026-10-05 | `adjustment_posting_id` is stored, as ARCHITECTURE.md names it, and the transaction id is what the API returns | The posting is the fact; the transaction is what a person can see in the list, so the answer points at the thing that can be opened |
| 2026-10-05 | The balance field is focused when the panel opens | The milestone is ten seconds, and the first thing a person does is type the balance their bank shows. Focus is the cheapest second saved |
| 2026-10-05 | The balance-check hooks live in their own module rather than growing `useAccounts.ts` | One file per concern: accounts and rates in one, the check and its share in the other. The cache keys they share are exported, so the invalidation still happens in one place |
| 2026-10-05 | A child whose branch was removed is still listed, after the branches | The name is still live and money is filed under it: hiding it would make a real figure unexplainable |
| 2026-10-05 | The migration names the foreign key it adds on `postings` | Alembic rendered `drop_constraint(None)`, so the downgrade would have failed the day it was needed. A constraint without a name is a trap, not a shortcut |
| 2026-10-06 | `_record` takes `Movement` value objects instead of `(account, amount, kind)` tuples | Splits made a fourth field arrive, and a bare tuple of three numbers was already the shape most likely to be silently transposed. The dataclass names each field and defaults the new one |
| 2026-10-06 | `roll_up` walks upwards from each amount and stops a cycle after one pass over the categories | The tree cannot hold a cycle, but a report that hung on one would be worse than a wrong total, and the guard costs one line |
| 2026-10-06 | The category tree lives in `features/categories/` and the transactions feature imports it, rather than the tree moving into `lib/` | It is feature data with its own calls and hooks, not a shared utility: the accounts feature is imported by transactions in exactly the same way. `lib/` stays for things with no feature of their own, like money and dates |
| 2026-10-06 | `CategoryPicker` is given its tree and does not fetch it | The page already holds the tree, and a component that fetches cannot be tested without a provider; the accounts form takes its accounts the same way. It takes an `id` and a `label` so several pickers can stand in a split's rows |
| 2026-10-06 | A transfer is offered no picker at all, rather than a disabled one | There is nothing to file: the server posts a transfer with no category, and an empty field would suggest one could be given |
| 2026-10-06 | A split is a mode on the form: the amount stays the whole, and the parts are a reading of it | The statement says one figure, so that figure is what the user states. `parts.ts` requires two parts or more and an exact sum, mirroring `parts_make_whole` on the server, and says how much is still to allocate so the parts can be made to add up |
| 2026-10-06 | A form sends `parts` or `category_id`, never both, and keeps both while the split is toggled | The server refuses a movement filed both ways. Keeping what was typed means a change of mind loses nothing; the flag decides which of the two the payload takes |
| 2026-10-06 | A row reads a movement by its shape: one posting, an internal movement, or a split | The list called a split `Transfer · SBI → SBI · ₹0.00` because "two postings" was read as a transfer. The three shapes are the ledger's own, so spending stays spending, the amount is the whole, and the account is named once. Found by the walkthrough, not by a test |
| 2026-10-06 | The editor's amount and the row's amount are the same function | They were two copies of the same arithmetic, and both were wrong for a split in the same way. One implementation in `describe.ts`, read by `edit.ts`, means a figure cannot be right on one screen and wrong on the other |
| 2026-10-06 | The spend report answers with the rows, the money in no category, and the period's whole | A row can only exist for a category, so uncategorised spending had nowhere to appear and the rows did not add up to what was spent. The whole comes back with them, so no client has to decide what counts as spending |
| 2026-10-06 | `GET /categories/spend` changed shape now rather than growing a second endpoint | Nothing consumed it yet, so the honest shape costs nothing today; a list that cannot be reconciled would have been the thing clients were written against. The nested response needs `from_attributes`, because its rows are dataclasses |
| 2026-10-06 | Every name in the tree is a row on the categories screen, children included | The first cut made only groups editable, which left 43 names that could not be renamed at all. A child is a name the user owns exactly as a group is, and the tree's indentation already says which is which |
| 2026-10-06 | The add form offers spending and earning only, and takes the kind only for a name that stands alone | A child carries its parent's kind, so asking would be a second answer; and an `adjustment` name can be created through the API but nothing offers it, so a form that offered one would be creating a name with no use |
| 2026-10-06 | A name is offered only the branches other than the one it is already in, and a branch holding names is offered none | Moving a name where it already is is not a move; and a branch with children cannot move at all, because the server refuses to leave them behind. The top level is added by the screen, because a name under a branch may always go up |
| 2026-10-06 | The spend view owns its period and starts on the month today falls in, and the report is dropped when the tree or the movements change | "Where did the money go?" is asked about a month, and a report is derived from names and postings alike: a rename changes what it says, a movement changes what it counts. Neither cache may outlive either change |
| 2026-10-06 | A row says what a movement was filed under, and nothing at all when it was filed under nothing | A split names its parts, an unfiled movement says nothing rather than "no category", and a transfer says nothing because it was never filed. Filing is only worth showing when it is a fact about the movement |
| 2026-10-06 | A write-off's wording lives in its filing and no longer in a note | M9 put the wording in the note because there were no categories; M10 gave it the real category, and both left the write-off saying its own name twice. The row now says it once, which is what the M9 decision asked M10 to finish |
| 2026-10-06 | A suggested name is one used in the last 90 days, offered by how often it was used, then by how recently, then by name | Most used is the chip the user means most of the time, and the two tie-breaks are what stop the row reshuffling: a list that moves for no reason cannot be learnt by thumb. A name dropped for three months stops taking up room in the row |
| 2026-10-06 | A suggestion remembers the *last* time a name was recorded - the account, the amount and the category - and a split remembers no category | One tap is one movement, so what it fills in has to be a fact, and the most recent time is the fact the user is most likely repeating. A split has several categories, so offering one of them would be a guess dressed as a memory |
| 2026-10-06 | Tapping a chip never overwrites an amount already typed, but fills it when the field is empty | The screen asks for the amount first, so the user is usually mid-way through it when a chip is tapped; overwriting what someone has just typed is the rudest thing a shortcut can do |
| 2026-10-06 | Fast entry reuses the recording form's rules rather than growing its own | Money, dates and validation are the parts that must not have two implementations. The daily screen is a faster way to fill the same values in, and `toPayload` is called exactly as before |
| 2026-10-06 | The daily screen reads two lists: today's entries, and the recent history for its shortcuts | They are different questions. "Same as yesterday" needs a day this screen does not show, and a shortcut that is disabled because of which list happened to be loaded is a bug - which is exactly what the walkthrough found |
| 2026-10-07 | The rule about which kind of name may file what became public (`file_under`) and is shared | A recurring item carries a category as a movement does, and the refusal has to read the same in both places. Copying those five lines would have been the start of two rules that drift |
| 2026-10-07 | The repeats list says the rhythm in words and promises no next date | A rent said as "every month on the 5th, or the last day when the month is shorter" is the whole truth about it. "Next due 5 Nov" would need an endpoint answering a question the rhythm already answers, and it would be a second place to be wrong |
| 2026-10-07 | Changing a plan sends only what changed, and its rhythm goes as a whole | The same rule a movement's correction follows, for the same reason: sending everything back would overwrite a change made elsewhere with whatever the row was opened with. The two halves of a rhythm have to move together, so they travel together |
