# DECISIONS

One line per non-obvious decision and why. The assistant adds to this after each approved milestone. Newest at the bottom.

| Date | Decision | Why |
| --- | --- | --- |
| 2026-10-04 | Money is integer paise everywhere; no floats | Rounding drift in a finance app is unrecoverable trust damage |
| 2026-10-04 | Balances are derived from postings, never stored as truth | Stored running totals drift |
| 2026-10-04 | Category lives on the posting, not the transaction | Splits come free: one payment, several postings |
| 2026-10-04 | Pots are child accounts (`parent_id`), one table | Slice goals, FDs and sub-balances need no special cases; net worth sums the tree once |
| 2026-10-04 | Python and FastAPI backend, React and TypeScript frontend | PDF and statement parsing is far stronger in Python; frontend ports to React Native later |
| 2026-10-04 | Sync SQLAlchemy 2.0 with psycopg 3, not async | Simpler and less error-prone for a single-user app built with a coding model |
| 2026-10-04 | Server-side sessions in Postgres with an HttpOnly cookie | Revocable and simple; mobile can use tokens later |
| 2026-10-04 | Everything runs in Docker; host needs only Git and Docker | Zero local toolchain setup, and local mirrors production |
| 2026-10-04 | No Redis, Celery, microservices or Kubernetes | Added only when something actually hurts |
| 2026-10-04 | Real balances and statements stay out of git (seed_local.json, data/samples, backups ignored) | Privacy; the repository may become shared |
| 2026-10-04 | Deploy to a budget VPS behind Caddy, backups kept off the server | Free tiers sleep or expire; the data is financial history and needs a stable home |
| 2026-10-04 | Work proceeds one milestone at a time with plan approval and a completion approval | Prevents large unreviewed changes from a coding model |
| 2026-10-04 | A dedicated `finance_test` database is created by the Postgres init script; tests run against real Postgres | Integration tests need a real database, and development data must stay untouched |
| 2026-10-04 | The backend container entrypoint runs `alembic upgrade head` before starting | A fresh database is always migrated, with no manual step |
| 2026-10-04 | The frontend health check reads only the HTTP status, not the JSON body | Avoids hand-writing a duplicate of the server schema; generated OpenAPI types come later |
| 2026-10-04 | Money parsing rejects more than two decimal places instead of rounding | A silently rounded amount is a wrong number the user would never see |
| 2026-10-04 | A split gives the remainder paise to the first parts | Deterministic, and the parts always sum back to the total with no paise lost or created |
| 2026-10-04 | Parsing accepts Indian and Western digit grouping but rejects malformed grouping | Real inputs vary, yet broken grouping almost always means a typo worth failing on |
| 2026-10-04 | The frontend mirrors only the money formatter, not a parser | The UI formats what the API sends; it never parses or does money arithmetic |
| 2026-10-04 | Passwords are hashed with Argon2 (argon2-cffi) | Memory-hard and the algorithm named in ARCHITECTURE; never stored or logged in clear |
| 2026-10-04 | Session tokens are random and stored only as a SHA-256 hash | A stolen database dump must not be replayable as a login |
| 2026-10-04 | One app-level auth guard with an allowlist, not per-route dependencies | A router added later is protected by default and cannot be exposed by forgetting a dependency |
| 2026-10-04 | `create-user` reads credentials from the environment, never CLI arguments | Passwords passed as arguments appear in shell history and the process list |
| 2026-10-04 | Login rate limiting lives in Postgres (`login_failures`), not in memory | CODING_STANDARDS section 6 needs a limit and section 3.1 forbids global mutable state; Postgres also survives restarts and extra workers |
| 2026-10-04 | Server state lives in TanStack Query; React keeps no copy of it | CODING_STANDARDS section 4.2: one cache, no duplicated server state |
| 2026-10-04 | The app swaps login and home on session state instead of adding React Router | Two screens do not justify a router dependency; routing arrives with real screens |
| 2026-10-04 | The M1 health placeholder (`HealthStatus`) was removed in M3b | The real login and home screens replace the placeholder page, so it became dead code |
| 2026-10-04 | Testing Library cleanup is registered explicitly in the test setup | Vitest runs without globals, so the library cannot auto-register it and the DOM leaked between tests |
| 2026-10-04 | Account `type` and `capture_mode` are VARCHAR plus a CHECK constraint, not Postgres enums | Adding a kind later is an ordinary migration instead of an `ALTER TYPE` every deployment must apply in lockstep |
| 2026-10-04 | `loan` is in `AccountType` even though MILESTONES.md M4 lists only eight kinds | ARCHITECTURE.md treats loans as accounts; the CHECK makes it cheap to allow now and impossible to forget later |
| 2026-10-04 | An account's `type` cannot be changed after creation | Postings, credit-card rules and importers key off it, so a change would silently reinterpret existing history |
| 2026-10-04 | A pot needs exactly one live, non-pot parent, enforced in the database and the service | The invariant is what makes pots and sub-balances work with no special cases, so it must not depend on one code path |
| 2026-10-04 | Service functions raise domain errors (`AccountNotFoundError`, `InvalidAccountError`); only routers map them to HTTP statuses | Keeps HTTP out of the logic layer and gives exactly one place per status code |
| 2026-10-04 | M4 was split into M4a (accounts) and M4b (interest rates) after the plan review | The account model and CRUD already exceed one reviewable step, and rate history needs its own tests |
| 2026-10-04 | Interest rates are dated rows that are never updated in place; a correction is a soft delete plus a re-add | SPEC.md line 49: a rate change is recorded, never overwritten. An update endpoint would silently rewrite what a provider paid, and when |
| 2026-10-04 | One live rate per (account, from_date), enforced by a partial unique index | A plain unique constraint would let a soft-deleted mistake block the corrected rate for the same date |
| 2026-10-04 | `rate` is NUMERIC(7, 4), a Decimal end to end, serialised as a JSON string, and more than four decimals is rejected rather than rounded | A rate must not drift through a float; a string carries the exact decimal, and silently rounding repeats the mistake the money parser refuses to make |
| 2026-10-04 | The rate schema quantises to the column's scale | The session is `expire_on_commit=False`, so a create echoed 7.1 while a later read returned 7.1000; the same record must not read differently per endpoint |
| 2026-10-04 | Rate routes hang off the accounts router and resolve the account through `get_account` | Ownership lives on the account, so there is one rule and no second path to another user's data |
| 2026-10-04 | A duplicate start date answers 409, not 400 | The payload is valid; it conflicts with an existing record, and 409 says that honestly |
| 2026-10-04 | The frontend parses money text into paise (`lib/money.ts`), mirroring `core/money.parse_paise` case for case | CODING_STANDARDS.md section 4.2 requires forms to parse money through the shared helper. This supersedes the M2 decision that the frontend would mirror only the formatter, which was made before any form existed; RULES.md puts the standards above DECISIONS.md |
| 2026-10-04 | `parsePaise` refuses an amount above `Number.MAX_SAFE_INTEGER` | JavaScript cannot hold such a number exactly, and a silently wrong balance is worse than a refusal. Python's integers on the server have no equivalent limit |
| 2026-10-04 | Frontend API types are generated from the live OpenAPI schema and the generator is called pinned through `npx`, not added as a devDependency; the generated file is committed and excluded from ESLint, but still Prettier-formatted and typechecked | `openapi-typescript` 7 peers `typescript` ^5 and this project is on 6. Installing it with `--legacy-peer-deps` churned 90 lines of unrelated lock entries and broke `npm ci` in the image build. Committing the output means nothing depends on the generator at run time or when the backend is down |
| 2026-10-04 | The accounts screen replaces the placeholder home page | Same reasoning as M3b removing the M1 health placeholder: a screen that no longer matches the product is dead weight |
| 2026-10-04 | An account's first interest rate is recorded from its opening date, in a second call after the account is created | The account is the object that matters, so a rate failure leaves it intact and reports exactly what did not save, rather than losing both to one transaction. The user is never asked for the same date twice |
| 2026-10-04 | Form option lists are declared `satisfies Record<Enum, string>` | A member added on the server becomes a compile error in the form, instead of an account type the UI silently cannot create |
| 2026-10-04 | The add and edit forms share one `AccountFields` component | Ten duplicated fields would drift apart, and the add form's tests are the safety net for the shared part |
| 2026-10-04 | An empty optional day is sent as `null`, never as `0` | `Number('')` is 0, which the server rejects: a credit card could not be saved unless both card days were filled. Empty means "not set", and zero is not a day of any month |
| 2026-10-04 | Removing a rate asks for confirmation first, and nothing is sent until it is confirmed | A rate is financial history; the guard costs one click and the dismissal is silent, so a mis-tap cannot quietly rewrite what a bank paid |
| 2026-10-04 | The edit form shows the type read-only, with the reason next to it, rather than hiding the field | The user still sees what the account is while changing it, and learns why that one field is fixed |
| 2026-10-04 | The seed skips an account that already exists by name instead of updating it | An opening balance that has since been corrected must never be overwritten by re-running a setup command; the fix belongs in the UI, where the change is visible |
| 2026-10-04 | Placeholder accounts carry a ` (demo)` suffix and a purpose note, and `--remove-demo` matches only that | Dummy data has to be removable later with no chance of deleting a real account that happens to share a name |
| 2026-10-04 | The seed writes nothing until all six accounts have been answered | An interrupted run, including piped input that ends early, must leave no half-created set behind |
| 2026-10-04 | The placeholder balance and date are fixed constants, not "today" | The placeholder run must give the same result on every machine and every day, so it can be tested and reasoned about |
| 2026-10-04 | A typed balance in the seed goes through `core/money.parse_paise`, and the prompt re-asks until it is accepted | The command-line tool must not grow a second money reader, and a typo must not become a wrong paise value |
| 2026-10-04 | Backups are `pg_dump --format=custom` in a dated file under `backups/`, and the script reads every file back before trusting it | A dump that cannot be listed is not a backup, and discovering that at restore time is discovering it too late |
| 2026-10-04 | `restore.sh` refuses the live database; restoring into a scratch copy is the only path it offers, and replacing live data is a documented manual sequence | One typo must not be able to replace financial history. Promotion should be a decision somebody makes, not a command away |
| 2026-10-04 | The backup scripts run through the `postgres:16` db container, so the client matches the server | `pg_dump` refuses to dump a newer server, and the backend image has no client at all; a mismatched client is a trap that only springs on the day it is needed |
| 2026-10-04 | The round-trip row-count check is a script rather than a pytest test | The host has only Git and Docker, so the check runs where the correct client already is. It is documented with the daily commands instead of hiding in a gate it cannot join |
| 2026-10-04 | The database name `finance_restore` is reserved for the scratch restore, and `finance_promote` for the documented promotion | The scripts drop and recreate those names on demand, so nothing else may own them |
| 2026-10-04 | A posting's amount is the signed change to that account's balance, and `kind` is what analytics reads | A card's outstanding is then simply a negative balance: no per-type sign rules, and one convention everything downstream can rely on |
| 2026-10-04 | Only the transaction carries a date; a posting is dated by its transaction | One date per movement, so a posting can never disagree with the transaction it belongs to |
| 2026-10-04 | An expense or income is one posting; a transfer is two that sum to zero | The other side of an external flow is the world outside the app, not an account. An internal movement that does not sum to zero would create or destroy money |
| 2026-10-04 | Amounts are given as positive numbers and the kind sets the direction | A sign typed by hand is a sign that can be typed wrongly; this makes `record_expense(-500)` impossible rather than merely discouraged |
| 2026-10-04 | A posting dated before the account opened is refused when written, and the ledger also ignores such a posting | Fail loudly on new data, yet stay correct for anything already stored, which imports will need |
| 2026-10-04 | The balance endpoint returns the opening balance and the postings total next to the answer | A figure that arrives without its parts cannot be checked, and this product's rule is that every number is explainable |
| 2026-10-04 | `category_id`, `import_batch_id` and `fingerprint` are left out of the models until M10 and M15 | Empty columns nothing writes are worse than a one-line migration later |
| 2026-10-04 | Recording a movement is one `POST /transactions` whose body is a discriminated union on `kind` (expense, income, transfer) | The three shapes share a date, a merchant and a note but differ in what they touch. One URL stays honest, and the discriminator refuses a malformed transfer before any code runs and hands the generated TypeScript client a union it can narrow on |
| 2026-10-04 | `transaction_date` is required when recording, and is never defaulted to today | The API does not read the clock on the user's behalf: the date of a movement is the one the user states. A silent "today on the server" default is a bug that only appears near midnight, and the UI is the right place to offer today |
| 2026-10-04 | A movement has no `kind` of its own in the response; the postings and their kinds are the answer | The transaction carries the date and each posting carries an amount and a kind. A top-level `kind` would be a second answer to "what is this?", free to disagree with the postings it is meant to summarise |
| 2026-10-04 | An edited amount is given as a positive number and the sign is recomputed from the posting's kind | The same rule as recording, so `-500` cannot turn an expense into an income one PATCH at a time |
| 2026-10-04 | An amount can only be changed when the transaction has exactly one posting; a transfer is refused with a message telling the user to delete it and record it again | Two postings that must sum to zero cannot both be rewritten from one amount without the caller naming both sides, and guessing which side moved could break the pairing. A 400 with that sentence in it is more useful than a wrong edit |
| 2026-10-04 | `PATCH` distinguishes an omitted field from an explicit `null` through `model_fields_set` | Correcting a date must not wipe the merchant and the note, so absent means "leave it alone" and `null` is the only way to empty a note. The date cannot be null at all |
| 2026-10-04 | Moving a transaction's date to before its account opened is refused, exactly as recording one would be | One rule applied at both points, so no edit can reach a state a create would have rejected |
| 2026-10-04 | `?from=` and `?to=` are aliased query parameters and both ends are inclusive | `from` is a Python keyword, and a range a user types as the 1st to the 31st should include both of those days |
| 2026-10-04 | An account reached on a write that does not exist, or is soft-deleted, answers 404 rather than 400 | The payload is well formed; the thing it names is not there. This is what the accounts routes already say, and a soft-deleted account is included on purpose: it may not be recorded against, and "no longer in use" says so |
